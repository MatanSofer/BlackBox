# Timeline Behavior — Design Clarification

> Documented from debugging session on 2026-03-01.
> Updated 2026-03-12: call log entries added to timeline; WiFi fingerprint place matching added.
> Covers what the timeline shows, why few records appear, and what is collected in the background.

---

## What the Timeline Screen Actually Shows

`GetTimelineUseCase` fetches **4 types** of entries:

| Type | `TimelineEntryType` | Source |
|------|---------------------|--------|
| Location stays | `LOCATION_STAY` | `locationRepository.getLocationsInRange()` |
| Activity transitions | `ACTIVITY` | `recordRepository.getRecordsByTypeInRange(CollectorType.ACTIVITY, ...)` |
| Call log entries | `EVENT` (iconType = `call_incoming` etc.) | `recordRepository.getRecordsByTypeInRange(CollectorType.CALL_LOG, ...)` |
| Derived events | `EVENT` | `timelineRepository.getEventsInRange()` |

**WiFi, Battery, Connectivity, ScreenState, AudioLevel, Barometer, Light** — all 7 of those collectors run and save to the DB, but they are **not shown in the timeline**. Their data is available for Search queries only.

### Place Name Resolution (Location Stays)

When building a `LOCATION_STAY` entry, the use case tries two methods to resolve a human-readable place name:

1. **GPS match** — `placeRepository.findNearestPlace(lat, lon)` checks if any `KnownPlace` is within its `radiusMeters`.
2. **WiFi fingerprint fallback** — if GPS match fails, checks WiFi records collected during that stay for a `connectedBssid` that matches any known place's `wifiFingerprint` list.

This means places with poor GPS (indoor offices, underground garages) can still show their correct name if you've added their WiFi BSSID to the place's fingerprint.

## Why You See Very Few Entries

### Location (1 entry for a whole day at one place)

- `LocationCollector` requests a GPS update every **5 minutes** (`DEFAULT_INTERVAL_MS = 5 * 60 * 1000`).
- Over 3 hours = ~36 location points are saved to the DB.
- `GetTimelineUseCase.buildLocationEntries()` **groups all points within 100 meters into a single `LOCATION_STAY`** (`STAY_RADIUS_METERS = 100.0`).
- Result: if you didn't move, all 36 DB rows collapse into **one timeline entry** showing the start time and total duration.
- The first GPS fix taking ~10–14 minutes after app start is normal (FusedLocationProvider warm-up).

### Activity (2 entries at startup)

- `ActivityCollector` is **event-driven**, using the `ActivityTransition` API.
- It only fires when you **change** activity (e.g., STILL → WALKING, WALKING → STILL).
- Only `ACTIVITY_TRANSITION_ENTER` events are recorded.
- If you stay still for 3 hours: 1–2 transitions at startup (initial STILL detection), then nothing more.
- This is correct and battery-efficient by design.

### Derived Events (0 entries during the day)

- Derived events are generated by `DailySummaryWorker`, which runs **once per day at end-of-day**.
- They are NOT generated in real-time.
- Today's timeline will always show 0 derived events while the day is still in progress.
- They appear the **next day for the previous day's data**.
- Examples of what they include: distance traveled, screen unlock count, top apps used.

## What IS Being Collected in the Background

All 10 collectors run via the foreground service and save to SQLDelight DB:

| Collector | Interval | Type |
|-----------|----------|------|
| `LocationCollector` | 5 min | Event-driven (FusedLocationProvider callback) |
| `ActivityCollector` | On transition | Event-driven (ActivityRecognition transitions) |
| `WifiCollector` | 5 min | Polling |
| `ConnectivityCollector` | 5 min | Polling |
| `AppUsageCollector` | 15 min | Polling |
| `ScreenStateCollector` | On change | Event-driven (BroadcastReceiver) |
| `AudioLevelCollector` | 60 sec | Polling |
| `BatteryCollector` | 5 min | Polling |
| `BarometerCollector` | 30 sec | Polling |
| `LightCollector` | 60 sec | Polling |
| `CallLogCollector` | 2 min | Polling (ContentResolver query) |

All records go to the `collected_records` table. Location also writes a denormalized row to `location_records` for fast spatial queries.

## Expected Timeline for a Stationary User (3 hours at home)

```
[08:02] ACTIVITY — STILL (Confidence: 100%)
[08:02] ACTIVITY — (possible second transition)
[08:14] LOCATION_STAY — (coords or known place name) — 2h 46m
```

This is correct behavior, not a bug.

## Known Design Limitations

1. **No real-time derived events** — the timeline has no live "significant moment" detection. Derived events are only end-of-day.
2. **Stationary users see minimal timeline entries** — by design. The timeline is a "meaningful events" view, not a raw sensor dump.
3. **All non-location/activity data is query-only** — WiFi, Battery, etc. are only accessible via the Search screen's NL query engine.
